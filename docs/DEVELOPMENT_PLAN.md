# 简历面试助手 MVP 开发计划

状态：总体 MVP 已实施基础版本；当前执行切片为“阶段一：OCR 简历提取与确认”。

## 当前执行切片

OCR 阶段已实现 PDF/DOCX 本地解析、图片型 PDF OCR、页级证据、本地规则结构化草稿和人工确认表单。当前执行切片继续实现 Agent 追问的第一条异步链路；上传、解析和确认过程仍不得调用 LLM。完整边界见 [Agent 追问需求](requirements/agent-follow-up.md)，执行顺序和进度以根目录 [PROCESS.md](../PROCESS.md) 为准。

当前识别草稿采用“完整描述优先”结构：技能掌握为一个 `content` 文本对象；工作/实习经历和项目经验按记录保留定位字段，但每条记录只有一个完整 `description`。历史拆分草稿通过 Alembic `0003_compact_resume_recognition`、`0004_clean_compact_resume_content` 迁移，阻止项目内容误入技能段并清理重复经历描述；原始 OCR 证据和已确认事实证据不被静默覆盖。

## 1. 目标

基于候选人的简历和真实项目证据，发现其理解缺口，并帮助候选人练习到能够独立解释自己的项目、回答面试者的追问。

MVP 是一个面向 Python 后端候选人的本地单用户 Web 应用。应用在本地保存材料，由应用组装上下文，并直接调用 LLM。MVP 不实现自主 Agent 工具或 Agent loop。

## 2. 范围

### 本期建设

- 创建材料集合，包含一份简历和零个或多个项目 ZIP 档案。
- 解析 PDF/DOCX 简历，图片型 PDF 使用 OCR 兜底。
- 全量识别个人信息、技能掌握、工作/实习经历和项目经验，并通过确认表单允许候选人修正。
- 在不执行上传代码的前提下安全检查 ZIP 内容。
- 保存证据位置：简历页码/段落，以及项目文件路径。
- 为同一个材料集合版本创建多个独立对话。
- 针对 Python 后端面试生成基于证据的问题（后续阶段）。
- 允许候选人选择简历文字并提出针对性问题（后续阶段）。
- 允许候选人用文本回答，并获得基于证据的反馈。
- 检测证据缺口，向候选人询问缺失细节。
- 将确认后的候选人补充内容作为独立证据保存，不修改原始文件。
- 删除单份当前材料或整个材料集合；单份删除保留历史版本，集合删除清理全部派生数据。

### 本期不建设

- 从空白开始创建完整简历的表单（上传后的识别确认表单属于本期范围）。
- 公开多用户账号、团队工作区或云端文件存储。
- GitHub/GitLab 仓库同步。
- 代码执行、构建、测试、沙箱或代码修改。
- 自主工具选择、ReAct loop、多 Agent 协作或网页搜索。
- MVP 中的跨对话长期记忆。
- 语音输入或语音反馈。
- 自动判断面试通过概率。

## 3. 推荐技术栈

| 领域 | 选择 | 原因 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 适合单页交互，开发速度快，生产环境不需要额外的前端服务器运行时。 |
| 前端数据 | TanStack Query | 处理上传、状态轮询、缓存失效和变更状态，避免手写请求状态管理。 |
| 后端 | Python 3.12 + FastAPI | 符合产品领域，也适合文档、代码解析和后续模型工作流。 |
| 校验 | Pydantic v2 | 统一校验 API 请求和 LLM 结构化响应。 |
| 持久化 | SQLite + SQLAlchemy 2 + Alembic | 适合本地单用户 MVP，并保留迁移到 PostgreSQL 的路径。 |
| 检索 | 基于证据块的 SQLite FTS5 | 不引入向量数据库，同时支持项目片段检索，行为容易检查。 |
| 文件存储 | 本地应用数据目录 | 原始文件和派生数据都在本地，删除范围清晰可审计。 |
| 简历解析 | PyMuPDF 和 python-docx | 解析 PDF/DOCX 文本及 PDF 页码信息。 |
| OCR | RapidOCR ONNX runtime 兜底 | OCR 在 Python 进程内运行，不需要单独部署托管服务。 |
| LLM 集成 | LangGraph + `langchain-core` + `langchain-openai` + Pydantic | LangGraph 编排短任务节点，`langchain-openai` 兼容现有 OpenAI-compatible 服务，API Key 只由服务端持有。 |
| 异步任务 | Celery + Redis | 将问题、反馈、参考答案和追问变成可重试、可取消、可轮询的后台任务。 |
| 代码检索 | 只读检索执行器 + `rg/grep` + Tree-sitter | 模型只生成结构化查询计划，执行器负责路径、文件和命令安全。 |
| 测试 | pytest + FastAPI TestClient；前端使用 Vitest | 覆盖解析、API 契约、删除、上下文组装和关键 UI 状态。 |

最小替代方案是只使用 FastAPI 和服务端渲染 HTML，不引入 React。它能减少初始化工作，但会让简历选中文本、上传进度和对话状态的演进变得困难。考虑到产品需要文档查看和交互式对话，推荐采用前后端分离的轻量方案。

## 4. 架构

```text
浏览器（React/Vite）
        |
        | HTTP + multipart upload
        v
FastAPI 应用
  |             |              |
  |             |              +--> Celery + Redis --> LangGraph Worker
  |             |                                      |-> LLM 适配器 --> 外部模型
  |             |                                      |-> 只读代码检索器
  |             |
  |             +--> SQLite（元数据、对话、任务、FTS5 证据索引）
  |
  +--> 本地数据目录（原始文件、抽取文本、OCR 产物）
```

浏览器永远不能取得 LLM 凭据。后端默认绑定到 `127.0.0.1`，打包或本地运行模式下由后端提供构建后的前端页面。

## 5. 领域与数据库模型

使用不可变的材料版本，确保旧对话仍然可以复现。

### 核心表

- `material_sets`：候选人的逻辑材料集合；包含标题、当前版本和创建/更新时间。
- `material_revisions`：一份简历及其项目成员关系的不可变快照标识。
- `materials`：原始上传文件元数据；包括类型（`resume` 或 `project_archive`）、文件名、内容哈希、大小、存储路径、解析状态和错误信息。
- `evidence_chunks`：抽取出的文本或代码片段；包括材料 ID、源文件路径、页码、行范围、片段顺序和内容哈希。
- `resume_extraction_drafts`：简历结构化识别草稿 JSON、处理状态、模型版本和更新时间。
- `resume_evidence_links`：结构化字段到页码、原文偏移和证据块的关联。
- `evidence_fts`：对证据片段文本及可检索元数据建立的 SQLite FTS5 索引。
- `conversations`：材料版本 ID、标题、状态、滚动摘要及创建/更新时间。
- `messages`：对话 ID、角色、文本、结构化响应 JSON、创建时间和模型元数据。
- `candidate_supplements`：对话 ID、材料集合 ID、内容、证据缺口引用、确认状态和来源消息 ID。
- `practice_turns`：一轮问题、回答、反馈、参考答案状态和轮次序号（Agent 阶段）。
- `question_versions`：问题文本、结构化范围、输入指纹、材料/项目/提示版本（Agent 阶段）。
- `reference_answers`：参考答案、证据等级、限制、代码快照和生成任务 ID（Agent 阶段）。
- `code_evidence_snapshots`：项目版本、文件路径、行号、代码片段、检索范围和内容哈希（Agent 阶段）。
- `llm_runs`：任务类型、节点、状态、输入指纹、耗时、结构化输出和错误摘要（Agent 阶段）。

### 关键不变量

- 一个对话必须且只能引用一个 `material_revision_id`。
- 原始上传文件不可变。
- 替换上传会创建新的材料版本。
- 证据引用必须能定位到现有证据块和源位置。
- 未确认的候选人补充内容不能作为材料集合证据返回给其他对话。
- 删除材料集合时，必须级联删除版本、对话、消息、补充内容、FTS 记录、抽取文件和原始文件。
- 删除材料集合时，必须级联删除练习轮次、问题版本、参考答案、代码证据快照和 LLM 任务。

## 6. 处理流程

阶段一只执行下列本地链路：上传 -> 文本解析/OCR -> 页级证据 -> 本地规则草稿 -> 人工确认。远程 LLM 链路从阶段一入口中排除。

### 简历导入

1. 校验扩展名、MIME 类型和文件大小。
2. 使用内部 ID 保存原始文件。
3. 按页或段落边界抽取 PDF/DOCX 文本。
4. 如果 PDF 没有可用文本层，运行 OCR 并保存逐页 OCR 结果。
5. 在保留源位置偏移的前提下规范化文本。
6. 将文本切分为带页码或段落引用的证据记录。
7. 使用本地规则生成个人信息、技能、工作/实习经历和项目经验识别草稿，不调用 LLM。
8. 将材料标记为 `ready`、`partial` 或 `failed`，将识别标记为 `awaitingConfirmation`，等待候选人通过表单确认。

### 项目导入

1. 校验 ZIP 大小、条目数量、压缩比例和路径穿越。
2. 拒绝绝对路径、`..` 穿越、符号链接和可能触发执行的压缩包行为。
3. 只将允许的文本类文件解压到隔离的材料目录。
4. 跳过 `.git`、`node_modules`、`target`、`build`、缓存、日志、二进制文件和超过单文件限制的文件。
5. 检测私钥、`.env` 内容和 API Token 等疑似密钥；在任何 LLM 请求前脱敏，并向候选人展示哪些内容被脱敏。
6. 将 README、依赖元数据、配置文件和源码文件建立为证据块。
7. 将项目标记为 `ready`、`partial` 或 `failed`，项目失败不能阻断简历使用。

任何导入步骤都不能导入或执行项目代码。

## 7. 兼容的直接 LLM 对话契约（旧版）

现有直接消息接口作为兼容能力保留。Agent 追问阶段改用第 14 节定义的 LangGraph 异步任务，不在 HTTP 请求中等待模型，也不使用自主工具选择或隐藏 Agent loop。

### 上下文组装顺序

```text
系统指令
+ 当前材料版本元数据
+ 完整解析后的简历，最多 40,000 字符
+ 相关项目片段，最多 24,000 字符
+ 对话摘要，最多 4,000 字符
+ 最近 8 轮对话
+ 选中文本（如果有）
+ 用户当前问题
```

项目片段优先使用用户明确选中的内容，其次使用 SQLite FTS5 做关键词相关性检索。应用永远不能把整个 100MB ZIP 发送给模型。

### 结构化响应

使用 Pydantic 校验模型返回结果后再保存：

```text
{
  answer: string,
  questions: [{text, type, evidenceIds}],
  evidence: [{evidenceId, quote, location}],
  inferenceDrafts: [{text, reason, requiresConfirmation}],
  evidenceGaps: [{question, missingDetail}],
  feedback: {strengths, missingPoints, nextPracticeStep} | null
}
```

如果结构化校验失败，带着校验错误和原始请求重试一次。如果重试仍失败，保存原始提供商错误用于诊断，并向用户返回可理解的失败信息；不能悄悄降级成没有依据的通用回答。

### 对话模式

- `generate_questions`：旧版兼容模式，可生成问题列表；Agent 追问阶段改为一次生成一条问题并保存问题版本。
- `selected_passage_question`：回答或澄清一个关于选中简历段落的问题。
- `answer_feedback`：从证据支持度、完整性、技术深度和表达清晰度评价候选人回答。
- `clarification`：针对证据缺口提出定向补充问题。

## 8. 后端 API

所有接口位于 `/api/v1` 下，JSON 字段使用 camelCase，错误响应使用 Problem Details。完整字段和状态码见 [REST API 契约](api/rest-contract.md)。

- `POST /material-sets`：创建材料集合。
- `GET /material-sets`：使用 `limit` 和 `offset` 列出本地材料集合。
- `POST /material-sets/{id}/materials?kind=resume|projectArchive`：统一上传简历或项目 ZIP，返回 202 和材料处理状态。
- `GET /material-sets/{id}/materials`：列出材料状态。
- `GET /material-sets/{id}/evidence`：列出可检索证据。
- `GET /materials/{materialId}/recognition`：获取简历识别草稿和状态。
- `PATCH /materials/{materialId}/recognition`：保存表单编辑后的识别草稿。
- `POST /materials/{materialId}/recognition/retry`：重试 OCR 或结构化识别。
- `POST /materials/{materialId}/retry`：重试项目档案静态解析。
- `POST /materials/{materialId}/recognition/confirm`：确认一个模块或全部模块。
- `POST /material-sets/{id}/conversations`：创建绑定到材料版本的对话。
- `GET /conversations/{id}`：返回摘要、消息和版本元数据。
- `POST /conversations/{id}/messages`：针对指定模式执行一次直接 LLM 请求。
- `PATCH /conversations/{id}/supplements/{supplementId}`：确认候选人补充内容。
- Agent 追问阶段使用 `/question-runs`、`/practice-turns/{turnId}/answers`、`/feedback-runs`、`/reference-answer-runs`、`/follow-up-runs` 和 `/llm-runs/{runId}`，完整契约见 [REST API 契约](api/rest-contract.md) 和 [Agent 追问需求](requirements/agent-follow-up.md)。
- `DELETE /material-sets/{id}`：返回 204，删除原始文件及全部派生记录。
- `DELETE /materials/{materialId}`：返回 204，从当前版本移除单份材料，旧版本和旧对话保持可读。
- `GET /health`：报告应用和数据库健康状态，不暴露密钥。

使用自动生成的 OpenAPI 类型或提交到仓库的 TypeScript API Client，避免前后端 Schema 静默漂移。

## 9. 前端流程

1. **材料集合**：创建命名集合，上传简历，可选上传项目，并查看解析状态。
2. **识别确认**：通过章节导航查看预填的个人信息、技能、工作/实习经历和项目经验表单，右侧按需打开原文依据，修改并按模块或全部确认。
3. **材料查看**：查看带页码的简历抽取文本，以及带解析/脱敏告警的项目文件树。
4. **问题工作区**：生成首轮问题、重新生成，或选择简历段落后提出针对性问题。
5. **对话**：展示用户消息、助手回答、可展开的证据、证据缺口和推断草稿。
6. **练习**：回答生成问题、请求反馈、确认候选人补充内容。
7. **删除**：从材料行删除单份材料，或从工作区删除材料集合，并清晰展示删除后的状态。

界面应就地展示解析和 LLM 错误，重试时保留用户已经输入的草稿，并且绝不显示服务端 API Key。

## 10. 交付阶段

每个阶段都必须可以独立使用。

### 阶段 1：应用基础

- 创建 `backend/` FastAPI 项目和 `frontend/` React/Vite 项目。
- 增加 SQLite Schema、Alembic 迁移、本地数据目录配置和健康检查接口。
- 增加材料集合创建、列表、单份材料删除、集合删除 API 及工作区 UI。

验收：用户可以创建和删除空材料集合；重启应用后本地元数据仍然存在；删除后数据库中不再有该材料集合记录。

### 阶段 2：材料导入和证据

- 实现简历抽取、OCR 兜底、ZIP 安全检查、文件过滤、密钥脱敏和证据切分。
- 实现简历结构化识别草稿、页级证据关联和人工确认表单。
- 增加上传状态和材料查看 UI。
- 增加 FTS5 索引和证据列表。

验收：普通 PDF、图片型 PDF、DOCX 和安全 ZIP 都能生成可追溯证据；四类简历模块能回填确认表单并定位原文；路径穿越和可执行压缩包测试样例会被拒绝；项目失败不影响简历使用。

### 阶段 3：直接 LLM 问题和对话（后续阶段）

- 增加模型提供商适配器和环境配置。
- 实现上下文组装、结构化响应校验、一次 Schema 修复重试和对话持久化。
- 增加问题列表、选中文本提问和可展开证据 UI。

验收：使用测试模型提供商 Stub 时，一个对话可以生成问题并回答选中文本；每个展示的证据 ID 都能定位到存储位置；不会发送整个 ZIP。

### 阶段 4：练习反馈和候选人补充

- 增加回答反馈模式和证据缺口澄清流程。
- 增加未确认补充内容状态和明确确认流程。
- 增加绑定材料版本的对话展示和完整删除级联。

验收：缺少指标时会产生澄清问题；候选人回复可以立即用于当前回答；确认后作为独立证据可见；删除材料集合后无法再次检索该内容。

### 阶段 5：MVP 加固

- 增加基于固定样例的 LLM 响应测试、上传限制、密钥脱敏测试和前端错误状态测试。
- 增加本地打包/启动脚本和简短的运维 README。
- 使用已配置的真实 LLM 提供商执行人工验收流程。

验收目标：抽查的问题中至少 80% 有效证据引用；测试用例中没有任何一个会执行上传代码；删除操作会移除所有原始和派生数据。

## 11. 配置与启动

服务端必需配置：

- `LLM_BASE_URL`：OpenAI-compatible 提供商接口地址。
- `LLM_API_KEY`：服务端持有的模型提供商凭据。
- `LLM_MODEL`：模型标识。
- `LLM_RESPONSE_FORMAT`：`json_object` 或 `none`，用于适配不同兼容服务。
- `LLM_AUTH_MODE`：`bearer` 或 `api-key`。
- `LLM_API_KEY_HEADER`：鉴权 Header 名称，默认 `Authorization`。
- `LLM_MAX_OUTPUT_TOKENS`：单次模型输出上限。
- `LLM_TEMPERATURE`：采样温度。
- `LLM_TIMEOUT_SECONDS`：请求超时时间。
- `LLM_MAX_RETRIES`：临时网络错误、429 和 5xx 的最大重试次数。

带安全默认值的可选配置：

- `APP_DATA_DIR=./data`
- `DATABASE_URL=sqlite:///./data/app.db`
- `MAX_UPLOAD_BYTES=104857600`
- `HOST=127.0.0.1`
- `PORT=8000`

MVP 唯一需要的外部账号是 LLM 提供商账号。OCR 和文档解析在本地运行。由于选中的简历/项目上下文会离开本机发送给 LLM，发布前必须核对模型提供商的数据保留和训练使用策略。

## 12. 验证与回滚

### 自动化检查

- 文本 PDF、图片型 PDF、DOCX、损坏文件和页码引用的解析测试。
- 路径穿越、符号链接、压缩比例、二进制过滤和密钥脱敏的 ZIP 测试。
- 上下文长度限制、选中文本、最近对话、摘要和版本隔离的组装测试。
- 上传、状态转换、结构化响应校验、补充确认和删除级联的 API 测试。
- 上传进度、重试、证据展开、反馈和删除状态的前端测试。

门禁命令固定为：`pytest backend/tests/unit -q`、`pytest backend/tests/integration -q`、`npm run test:e2e`。跨组件修改不得跳过端到端门禁。

### 人工验收

1. 创建材料集合，上传文本 PDF 和项目 ZIP。
2. 确认简历页码和项目文件位置都能正确显示。
3. 生成 8 个问题，确认每个问题都有证据。
4. 选中简历段落并提问。
5. 询问材料中缺失的指标，确认助手会向候选人提问。
6. 回答生成问题并请求反馈。
7. 确认候选人补充内容，验证它与原始简历分开保存。
8. 在同一材料版本上创建第二个对话，验证对话历史彼此隔离。
9. 删除材料集合，确认它不能再被列出、检索或查询。

回滚采用文件级和迁移级方式：停止本地服务，恢复 `data/` 目录和 SQLite 备份，再运行上一版本应用。MVP 不需要外部数据迁移。

## 13. 最脆弱的前提

本计划假设第一轮验证使用本地单用户 Web 应用即可。如果未来需要多用户、远程访问或云端持久化，则必须在对外暴露服务前，将 SQLite/本地文件和无认证边界替换为 PostgreSQL、对象存储和身份认证。

## 14. 阶段 5：Agent 追问与项目参考答案（第一条实现切片已完成）

本阶段以 [Agent 追问与项目参考答案需求](requirements/agent-follow-up.md) 为唯一行为基准。目标是让候选人选择问题范围、回答模型生成的问题，并按需获得有代码证据支撑的参考答案和反馈。

### 14.1 设计约束

- 问题不局限于简历事实，但必须绑定候选人选择的问题范围、材料版本和已确认证据边界。
- 问题由模型生成，候选人不能直接编辑；调整范围或点击“换一个问题”会创建新问题版本。
- 保存回答不调用 LLM；只有生成问题、查看反馈、查看参考答案和继续追问四个显式操作创建 LLM 任务。
- 参考答案必须绑定问题版本、项目档案版本和代码证据快照；输入指纹不变时直接复用，不重复生成。
- 代码档案只允许安全的只读检索和静态解析；禁止执行、构建、测试、安装依赖和网络访问。
- 业务数据库是唯一事实来源；LangGraph 只在 Worker 中执行一次用户动作，不在图内等待用户输入。

### 14.2 顺序任务

1. **领域模型与迁移**：已新增 `practice_turns`、`question_versions`、`practice_answers`、`practice_feedback`、`reference_answers`、`code_evidence_snapshots` 和 `llm_runs`；阶段六使用 Alembic `0005_agent_final_practice` 保存回答版本、反馈和追问父子关系。
2. **异步任务基础设施**：已增加本地队列适配器、Celery/Redis 配置入口、状态机、显式重试和取消接口；Docker Redis 7 + Celery worker 已完成真实消费验收，并覆盖队列不可用 Problem Details。
3. **LangGraph 与 LangChain 工作流**：问题、反馈、参考答案和继续追问分别使用带业务节点名称的短图；所有真实模型调用经 `LLMClient -> LangChainOpenAIAdapter -> ChatOpenAI`，结构化响应使用 `json_mode + Pydantic`，不在图内等待候选人输入。
4. **只读代码检索器**：已实现隔离目录、路径白名单、排除目录、文本文件读取和行号证据；查询计划的关键词、路径、命令注入、文件数和读取上限均由安全校验器约束。
5. **问题与参考答案版本**：实现完整问题范围、问题版本、回答版本、反馈持久化、输入 fingerprint 和 `insufficient` 空代码证据降级；用户修改回答不改写同一问题版本下的参考答案。
6. **REST API 与权限**：实现 `question-runs`、练习轮次回答、反馈任务、参考答案任务、继续追问、任务查询/重试/取消和轮次查询接口，全部返回 camelCase 和 Problem Details。
7. **前端练习工作区**：已增加问题范围选择、类型/难度/主题、可恢复多对话、异步任务进度、回答版本、反馈、参考答案和继续追问按钮；页面明确展示代码证据暂未启用。
8. **对话与删除链路**：只读取已确认事实和当前材料版本；材料集合删除时清理轮次、任务、问题版本、参考答案、代码快照和补充内容。
9. **测试和文档门禁**：先写失败测试，再实现；同步 API、功能链路、架构、需求和验收文档；三层测试全部通过后才可标记阶段完成。

### 14.3 阶段验收

- 单元测试覆盖问题范围/fingerprint、任务状态、幂等、版本复用、证据等级和代码检索安全边界。
- 集成测试覆盖 `202 + runId`、任务轮询、Worker Stub、保存回答不调用 LLM、参考答案版本隔离、失败重试和删除级联。
- 端到端测试覆盖选择范围、生成问题、保存回答、查看反馈/参考答案/继续追问、重复查看复用、修改范围生成新版本、取消任务和结束练习；当前自动化烟测已覆盖生成问题、回答保存和删除链路，反馈/继续追问由后端集成测试覆盖。
- 人工验收确认参考答案中的项目事实均可跳转到文件路径和行号；证据不足时不出现模型臆造的实现细节。
- 任何一个必需测试层级失败，或 API/领域/功能链路文档未同步，阶段均视为未完成。
