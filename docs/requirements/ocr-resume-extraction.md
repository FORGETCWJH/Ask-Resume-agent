# 阶段一：OCR 简历提取与确认需求

状态：已确认，阶段一已实现

## 1. 阶段目标

让用户上传 PDF 或 DOCX 简历后，在不调用任何 LLM 的前提下完成本地文本解析、图片型 PDF OCR、页级证据保存和简历信息结构化预填。用户可以在白色简约风格的确认页面中修正识别结果并保存，确认后的内容作为后续阶段可使用的简历事实。

本阶段只解决“把简历可靠地变成可追溯、可编辑的结构化内容”。问题生成、对话、回答反馈、候选人补充内容和 Agent loop 均不在本阶段实现。

## 2. 范围

### 2.1 本阶段包含

- PDF 和 DOCX 简历上传。
- 文本型 PDF 使用文本层解析。
- 图片型 PDF 按页使用本地 OCR。
- DOCX 按段落和表格提取文本。
- 原始文件、解析文本和页级/段落级证据保存。
- 使用本地规则生成四类结构化草稿：个人信息、技能掌握、工作/实习经历、项目经验。
- 简历确认页面：编辑字段、查看原文证据、保存草稿、按模块确认、确认全部。
- OCR 或解析部分失败时保留成功内容，并支持局部重试。
- 材料版本和识别草稿状态可查询、可恢复。
- 删除材料集合时清理本阶段产生的原始文件、解析文本、证据、草稿和派生文件。

### 2.2 明确不包含

- 任何 LLM 调用，包括上传后的结构化识别调用。
- 点击生成问题、问题批次、对话、回答反馈和澄清问题。
- LangGraph、LangChain4j、Redis、RabbitMQ 或其他 Agent/队列中间件。
- 上传项目代码的深度分析；项目 ZIP 仍只允许静态读取，是否接入简历确认由后续阶段决定。
- 从空白创建简历。
- 教育经历、奖项、出生日期、身份证号、详细住址和照片等固定字段识别。

## 3. 用户流程

```text
创建材料集合
  -> 上传 PDF/DOCX
  -> 立即返回材料 processing 状态
  -> 本地解析文本层或逐页 OCR
  -> 保存不可变原始证据
  -> 本地规则生成结构化草稿
  -> 前端轮询并进入简历确认页
  -> 用户修改字段并保存
  -> 查看字段证据和页码/段落
  -> 按模块确认或确认全部
  -> 保存为后续阶段可用的简历事实
```

上传 HTTP 请求不得等待 OCR 全部完成；本地处理使用可恢复的后台任务或受控异步执行。当前不需要远程队列，任务状态先由现有数据库状态和应用内任务管理承载。

## 4. 识别模块

### 4.1 个人信息

- 姓名
- 手机号
- 邮箱
- 所在城市
- 求职方向
- GitHub、博客、个人主页等链接

联系方式和个人链接只由本地规则提取，不发送到任何远程服务。

### 4.2 技能掌握

以一个完整 `content` 文本保留简历中的技能描述、证据引用和编辑来源。不拆分技能分类，不生成技能标签，不根据技能名称推断熟练度、年限或等级。

### 4.3 工作/实习经历

父记录包括公司、职位、开始时间、结束时间、经历类型、一个完整 `description` 和证据引用。工作/实习经历不再包含嵌套项目，也不生成背景、职责或指标字段。

### 4.4 项目经验

包括项目名称、时间范围、角色、核心技术、一个完整 `description`、链接和证据引用。`projectArchiveId` 在本阶段保留为空或已有值，不执行自动绑定。原文中的成果指标只并入描述，不单独展示。

### 4.5 历史草稿迁移

迁移版本 `0003_compact_resume_recognition` 将既有拆分草稿改写为紧凑结构；`0004_clean_compact_resume_content` 清理项目字段误入技能段，并去除工作/实习经历的重复描述。迁移只改写草稿 JSON 和字段关联路径，不改写原始 OCR 证据或已经生成的事实证据。

## 5. 状态和错误

### 5.1 材料状态

| 状态 | 含义 |
|---|---|
| `processing` | 正在解析或 OCR |
| `partial` | 部分页面成功，存在失败页面或告警 |
| `ready` | 已生成可用原始证据 |
| `failed` | 无法生成可用文本证据 |

### 5.2 识别状态

| 状态 | 含义 |
|---|---|
| `pending` | 等待本地结构化处理 |
| `processing` | 正在生成本地结构化草稿 |
| `awaitingConfirmation` | 草稿可编辑，等待用户确认 |
| `confirmed` | 模块已确认，可供后续阶段读取 |
| `failed` | 结构化处理失败，可重试或手动填写 |

OCR 失败页必须保留页码和错误原因；成功页不可因失败页而删除。重试失败页时，只替换该页的解析结果和关联，不覆盖其他页或用户已保存的草稿字段。

## 6. 确认页面

采用白色为主、简约、可扫描的工作台界面：

- 左侧显示四个模块导航和当前确认状态。
- 中间显示可编辑表单。
- 右侧以抽屉或弹窗显示只读原文证据、页码、段落和来源。
- 缺失字段显示为空或“未识别”，不能显示推测内容。
- 低置信度、OCR 失败页和解析告警必须有明确提示。
- 支持保存草稿、确认当前模块、确认全部、重试失败页和手动补填。

确认模块后，生成独立的结构化事实证据；未确认草稿只能留在确认页面，不能被后续对话阶段当作事实使用。

## 7. API 范围

本阶段保留并收敛以下接口，全部使用 `/api/v1` 和 `camelCase`：

- `POST /material-sets/{id}/materials?kind=resume`：上传后返回 `202` 和材料状态。
- `GET /material-sets/{id}/materials`：查看材料处理状态。
- `GET /materials/{materialId}/recognition`：获取本地识别状态、草稿和告警。
- `PATCH /materials/{materialId}/recognition`：保存编辑后的草稿。
- `POST /materials/{materialId}/recognition/retry`：重试全部解析或指定 PDF 页。
- `POST /materials/{materialId}/recognition/confirm`：确认模块或全部模块。
- `GET /material-sets/{id}/evidence`：查看原始证据。
- `DELETE /materials/{materialId}`：从当前材料版本移除单份材料，保留历史版本和旧对话引用。
- `POST /materials/{materialId}/retry`：重试项目档案的静态解析。

本阶段不新增问题生成、对话或 LLM 任务接口。错误响应继续使用 Problem Details，并包含稳定 `code`。

单份材料删除采用不可变版本策略：服务创建一个排除目标材料的新当前版本，旧版本、旧对话、旧证据和底层文件保留；删除整个材料集合时再统一清理文件和全部派生数据。只能删除当前版本中的材料。

## 8. 验收标准

### 自动化

1. 文本型 PDF、图片型 PDF 和 DOCX 可以完成本地解析流程。
2. 原始文件、页级/段落级证据和结构化字段可通过材料版本关联。
3. 全流程不发起 LLM 请求，不依赖 API Key。
4. OCR 单页失败时，成功页仍可查看、编辑和确认。
5. 草稿编辑不会修改原始文件或 OCR 原文。
6. 新材料版本不会覆盖旧版本草稿和证据。
7. 删除材料集合会清理本阶段全部数据。

### 人工

1. 上传一份文本型 PDF，确认四个模块均能展示。
2. 上传图片型 PDF，确认页码与 OCR 原文可定位。
3. 修改技能或项目字段后刷新页面，草稿仍然存在。
4. 只确认技能模块，其他模块保持未确认。
5. 触发失败页重试，确认成功页面和用户草稿不丢失。
6. 确认全部后，重新打开页面状态仍为已确认。
